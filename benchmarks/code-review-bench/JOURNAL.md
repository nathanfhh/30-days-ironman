# 建置手記：我怎麼幫自己的 skill 蓋一座考場

這篇不講分數，講過程。分數與方法論在 [`REPORT.md`](REPORT.md)。

這裡記的是：從「我想知道這個 skill 好不好」到「我有 1,395 條逐條驗證過的資料」之間，中間那段路長什麼樣，踩到什麼，改過什麼，以及哪些地方我一開始就做錯了。

---

## 0. 一個沒辦法自己回答的問題

`nathan-code-review` 是我寫的 Claude Code skill。它會跑掃描器、跑九個面向的檢查、要求每個「這裡壞了」的斷言先去找反證，最後產出一份繁體中文報告。

我用它用了一陣子，覺得還行。

但「我覺得還行」是所有評估方式裡最不可靠的一種——尤其當被評估的東西是我自己寫的，而評估的方式是我自己讀它的輸出。作者腦中有意圖，會把「我知道我想講什麼」誤讀成「它講清楚了」。這件事我在 repo 的 `CLAUDE.md` 裡寫過，用來規定 eval 的 judge 一定要是 subagent。現在輪到我自己被這條規則綁住。

所以要有一把外面的尺。

### 先說清楚我平常怎麼用它

不然後面「benchmark 跑的是什麼」會很模糊。

日常情境是這樣：同事開了一個 GitLab merge request，我在 Claude Code 裡把 MR URL 貼進去，說「幫我看一下」。接下來 skill 自己跑：

1. **preflight** 先盤點環境——哪些掃描器在、GitLab token 有沒有、Semgrep rules 在哪。**缺什麼不會靜靜跳過，會記進報告的 `scans[]` 並在發佈的內容裡揭露。**
2. **intent check**——這個改動該不該做？該不該在這個 MR 做？時機對嗎？這一步跟找 bug 無關，是問「這個 MR 本身合不合理」。
3. clone 到 `/tmp`，本地算 diff。
4. **掃描**——ruff / ty / oxlint / opengrep / trivy，各自一個 subagent，結果要歸因到這次改動，不是整個 repo 的存量問題。
5. **深度審查**——`ncr-fresh-eyes` 先在沒有任何 checklist 的狀態下看一遍，然後才跑九個面向。
6. **交付**——寫成 JSON、驗 schema、`ncr-quality-check` 稽核一遍、**問過我才發佈**，最後貼成 GitLab discussion，繁體中文。

還有兩條我沒在 benchmark 裡跑到的分支：**re-review**（同一個 MR 上次審過，這次只看增量）和 **pushback**（作者不同意某個 finding，這時候不重跑 pipeline，改去重新評估立場——包含承認自己錯了）。

**所以 benchmark 量到的是第 3 到第 5 步，加上報告產出。** 發佈前的把關、以及所有對話式的往返，都沒有被評分——而那恰好是日常用起來最常觸發的部分。這是這份成績單的邊界，先講在前面。

## 1. 先讀考卷，不要先答題

我挑的是 [withmartian/code-review-benchmark][crb]：50 個真實 PR、人工標註的 golden comments、41 個商業工具已經跑過的分數。

第一件事不是跑，是**讀它的原始碼**。

讀完發現一件關鍵的事：這個 benchmark 有兩半。線上那半要付費 API key、要驅動真的工具；線下那半把所有工具的候選清單和 judge 結果都存成 JSON 出貨了。也就是說，**同業的答案卷是現成的**，我不需要重跑他們，只要確保我的工具讀到同一張考卷。

這個發現決定了整個 harness 的形狀：我要做的不是「跑一個 benchmark」，是「插進一個已經跑完的 benchmark 的中間」。

第二件事，讀 scorer 的算法：

```python
precision = 命中的 golden comment 數 / 候選總數
```

我當下就知道會發生什麼——這個 skill 話很多。但我沒有改指標，也沒有預先寫任何辯解。**先照它的規則跑一遍，拿到那個數字，再來談那個數字在說什麼。** 順序反了就變成先射箭再畫靶。

[crb]: https://github.com/withmartian/code-review-benchmark

## 2. 第一個坑：diff 到底從哪裡來

這是整趟最接近「全部作廢」的一次。

直覺做法是：benchmark 說這是 `sentry#77754`，那就去 GitHub 抓 `sentry/sentry` 的 PR #77754 的 diff。

我照做了，然後去比對同業的候選清單——對不上。他們講的東西有些根本不在我的 diff 裡。

回去翻 benchmark 的 repo 結構，才看懂：**它為每一個工具各 fork 了一份 PR**，目錄名長這樣：

```
code-review-benchmark/<repo>__<sha>__augment__PR<n>__<sha>
```

工具審的是那個 fork 裡的 PR，不是上游那個。兩者的 base 可能差很遠——上游 PR 的 base 是當時的 master，fork PR 的 base 是 fork 的預設分支。

如果我沒發現，整份比較就是拿我對 A 的答案去比同業對 B 的答案。分數會有，名次會有，圖表會很好看，而且**完全沒有意義**。

修法是把 fork 釘死：

```python
DIFF_FORK_TOOL = "augment"
# 每個工具的 fork 都帶同樣的 commits，釘死一個
# 可以讓輸入 byte-identical，並消掉「選哪個 fork」這個變數
```

**教訓**：在做任何比較之前，先證明你跟對照組讀的是同一批 bytes。不是「應該是」，是去驗證。我後來驗證的方式很土——拿同業的候選清單去 grep 我的 diff，看他們提到的識別字在不在裡面。

（這條反射後來救了我第二次。跑到後面，有個審查 agent 回報「這份 diff 根本不是它標題說的那個 PR」。我沒有直接信，也沒有直接否定，而是去查同業對這個 PR 的候選——他們講的東西全部在我的 diff 裡。所以**標題是錯的，diff 是對的**，上游自己的註記也寫了 `there is no such PR, it is a mix of many PRs`。留下、照常計分、寫進 `NOTE.md`。）

## 3. 把規則寫死在讀答案之前

一開始 50 個 PR 我沒有全跑，成本不允許。那就要抽樣，而抽樣是最容易偷偷作弊的地方。

我的做法是把選取規則寫進腳本的 docstring，**在讀任何一條 golden comment 之前**：

```
- Python 主線 —— 全部 10 個 sentry* PR，不抽樣。
- 其他語言 —— 每個 repo 取 PR 編號最小的兩個。
```

「編號最小」是刻意選的：它跟難度無關、跟內容無關，而且事後無法調整。如果我寫「隨機取兩個」，我就有一個可以反覆重抽到滿意為止的旋鈕。

**這條規則後來確實咬了我。** Go 只有兩個 PR，其中一個是純改名的 chore——這對 recall 很不利，因為純搬移的 diff 裡真的沒什麼好講。但規則就是規則，我沒有換掉它，只在報告裡寫清楚 Go 的樣本是什麼組成。

**後來我把配額整個拿掉，跑完全部 50 個。** 這件事的方向很重要：解除配額只能**擴大**涵蓋，不能挑選，所以它不是一個可以調到滿意為止的旋鈕。而擴大之後，最弱的那部分結論確實被修正了——19 個 PR 時 Go 只有 2 個、我排第三；50 個 PR 時 Go 有 8 個、我還是第三，但前三名擠在 82–85%，以雜訊底線來看根本分不出高下。原本那句「不要當成語言能力排名」的免責，在 15 個 TypeScript、9 個 Java、9 個 Python、8 個 Go、6 個 Ruby 之後就不需要了。

## 4. 四個階段，四份 prompt

上游有三處外部 LLM 呼叫。我沒有 API 額度，就用 subagent 換掉，變成四個階段：

| 階段 | 做什麼 | 為什麼要獨立 |
|---|---|---|
| **review** | 跑我的 skill，產出報告 | 這是被測物 |
| **extract** | 把 zh-TW 報告正規化成英文 claim 清單 | 不然量到的是語言隔閡 |
| **judge** | 比對 claim 與 golden comment | 取代上游的 judge model |
| **verify** | 盲測驗證每條 claim 是否為真 | 這是後來才長出來的（見第 7 節） |

每個階段一份 prompt，存在 `harness/prompts/` 下，agent 被要求「完整讀完再開始」。這樣做的好處是**指令有版本控制**，不是散在對話裡；壞處是我得把每個階段的邊界想清楚才寫得出來。

幾條刻意設計的隔離：

- **review agent 不准讀 `data/` 底下自己 diff 與輸出目錄以外的東西**，也不准連網。它不能看到 golden comments，不能看到同業講了什麼。
- **judge 不讀 diff**。它只比對兩段描述講的是不是同一件事。這是上游 judge 的設定，我照抄——judge 一旦開始自己判斷對錯，它就變成第二個審查員，而不是配對器。
- **extract agent 不准讀 diff 和 checkout**。它的工作是翻譯與正規化，不是查證。

## 5. judge 是代餵的，所以它必須先被量

整套流程建立在「用 subagent 取代 API 呼叫」上。這句話聽起來很順，但它是一個未經檢驗的假設：**我的 judge 跟上游的 judge 是同一把尺嗎？**

這件事剛好可以驗證，而且免費。同業的候選清單是上游 judge 讀過的同一批 bytes，而上游用三個不同的 judge model 各發表過一次結果。所以我把我的 judge 套在同業身上，跟他們三個比：

| 工具 | 我的 judge | opus-4.5 | sonnet-4.5 | gpt-5.2 |
|---|---:|---:|---:|---:|
| cubic-v2 | 61.5% | 61.8% | 61.4% | 59.0% |
| augment | 52.6% | 53.5% | 53.4% | 49.6% |
| greptile-v4-1 | 44.4% | 44.0% | 40.4% | 39.5% |
| coderabbit | 35.9% | 35.2% | 37.1% | 33.3% |
| claude-code | 35.9% | 37.6% | 34.8% | 33.0% |

我跟他們均值的最大偏差是 3.1 個百分點，而**他們三個彼此之間的最大歧異是 4.5 個百分點**。名次對 sonnet-4.5 和 gpt-5.2 完全一致；對 opus-4.5 有一處對調——coderabbit 與 claude-code，而那兩家在我的 judge 下同分 35.9%，本來就分不出先後。

這件事給了兩個東西。一是「代餵的 judge 沒有引入新的誤差來源」不再是宣稱，是量出來的。二是一個我原本沒想到要有的東西：**雜訊底線**。在這個資料集上，4–5 分以內的 F1 差距不代表工具品質差異。後面看分語言數字時，這條線讓我少寫了好幾句過度解讀。

## 6. 執行時撞到的現實

理想的 harness 圖畫完，開始跑，然後現實開始扣分。

**subagent 裡不能再派 subagent。** 這是最痛的一個。我的 skill 靠 subagent 做掃描和 fresh-eyes，但整個 review 階段本身就跑在 subagent 裡。結果是 `ncr-fresh-eyes` 沒辦法在它該在的位置（讀 checklist 之前）執行。

我的處理是：讓外層補跑，再回填進報告，並且**把 stage 1 的報告原封不動存成 `report.stage1.json`**。這樣「fresh-eyes 之前的樣子」和「之後的樣子」都在版控裡，任何人都能算出它到底貢獻了什麼。

這不是一個好的修法。順序沒守住就是沒守住——fresh-eyes 的設計理由是「還沒被 checklist 框住的眼睛」，事後補跑的獨立性成立（它沒看過審查員的發現），但「在讀 checklist 之前」這個位置永遠地失去了。而且覆蓋很窄：首跑那 19 個案例裡，只有 10 個 Python PR 事後補跑並回填（那 10 份留有 `report.stage1.json` 可比對）；同一批的另外 9 個非 Python、以及後來補齊的 31 個，都沒有跑。**50 個裡實際覆蓋 10 個。**`ncr-quality-check` 則是 50 份全都沒跑。

**這些我全部寫進報告的揭露清單，而不是靜靜地讓它過去。** 一個沒跑完整的流程拿到的分數，跟跑完整的流程拿到的分數，不是同一個數字。

**掃描器幾乎全部不在。** 只有 ruff 可用；trivy、opengrep、ty、oxlint 都沒裝，而且不能為了裝它們去連網——這在 repo 的 `CLAUDE.md` 裡是硬性規則（`uv sync` 會執行受審分支控制的 build backend）。結果是 Java / Ruby / TypeScript 的 diff **完全沒有任何自動化靜態分析**，純靠模型讀。（Go 那批其實有 toolchain，是我在 prompt 裡寫錯了——見第 15 節。）每份報告的 `scans[]` 都如實列出哪些跑了、哪些沒跑。

**subagent 讀檔會靜默截斷。** 這個是抽取階段的 agent 自己抓到的：一份 436 行的 `report.json` 被截在第 415 行，藏掉了最後一個 finding。它是靠 `wc -l` 對照才發現的，然後回頭重讀。我之後在後續的 prompt 裡加了一句「檢查行數對不對」。

如果它沒發現，我會少掉一個 finding，而且**完全不會有人知道**——沒有錯誤訊息，沒有例外，就只是少了。這是這趟裡最讓我不安的一種失敗：安靜、無症狀、只有主動去對帳才看得見。

## 7. 第一個分數，和停下來的那一刻

跑完，算分：

**最後一名。F1 22.0%，precision 13.0%——第二差的一半。**

這裡是整趟的分岔點。有兩條路：

一條是接受，寫一篇「我的工具不夠好」的誠實檢討。這條路很安全，也很符合「不要幫自己找台階」的直覺。

另一條是問一個更基本的問題：**這個分數在量什麼？**

我選第二條，但選的時候心裡很清楚它的風險——「檢討指標」跟「找藉口」在外觀上一模一樣。差別只在於，你是不是願意讓檢討的結果有可能對自己不利，以及你用什麼方式去驗證。

先看數字的形狀：**recall 最高，precision 最低**。這不是「找不到問題」，是「講太多話」。775 個候選對 137 條 golden comment。

再回頭看那個公式，分子的上限是 golden 的數量。所以：

> 我講 775 件事，就算**每一句都是對的**，precision 的天花板也只有 17.7%。

這時候我知道問題在哪了：**這個指標沒有在區分「說得多」和「說錯」。**

但知道不等於證明。「那 671 個 false positive 其實是真的」在這個階段仍然只是我的自我主張，而且是一個對我極為有利的自我主張。要讓它有意義，得找一個我沒辦法作弊的方式去驗證。

## 8. 設計一個我作弊不了的驗證

這裡要先幫上游講句公道話，因為我後來去把 `methodology/full.md` 整份讀完了，而它比我原本以為的誠實得多。

那份文件裡有一段叫 **"Known limitations of the current implementation"**，開頭是：

> The current implementation is deliberately minimal — a starting point we can measure and improve against.

然後逐條自己列出：gold set 封頂在人類水準、bug 定義沒有條件化、judge 是單一模型單一 prompt 且沒有校準過。

**所以我要做的事，他們早就寫下來了。** §6 甚至把解法命名為 adversarial validation，§12 的 Stage 2 roadmap 裡明寫 `Begin adversarial validation`。

差別只在一件事：**文件寫了，程式碼還沒做。** `offline/` 底下 grep 不到任何相關實作。

這個分辨很重要。我一開始的草稿寫的是「他們提出了解法但沒實作」——那句話暗示疏漏。實際情況是排程：他們把 online benchmark 當 Stage 1 的頭條指標，offline 這半邊明講是「supporting role while we validate and improve it」。

所以我在做的不是補他們的洞，是**把一個排在後面的項目提前跑一次**。設計是這樣的：

每個 PR 蒐集一個池子，放兩種東西——

1. 全部的 golden comments（人寫的）
2. 全部工具沒對上的候選（六個工具，包含我的）

然後**把來源標籤全部拔掉**，用 slug 的 sha256 打散順序，重新編號 c001、c002……丟給一個獨立的驗證 agent，它拿到真實的 diff 和完整 checkout，逐條判 `real` / `not_real` / `unclear`，每條要附 `file:line` 證據。

關鍵在這一句，我把它寫進了 verify prompt：

> 驗證員不知道哪些 claim 是人寫的。

這是整個設計的重點。**同一個讀者、同一把尺，同時量「標準答案」和「被標準答案否決的東西」。**

少了這一步，我能得到的最好結果也只是「我的工具說它自己是對的」。加上這一步，golden comments 也在受審——如果人寫的那些全部通過，那 benchmark 沒問題，是我的工具話多；如果沒有，那就是另一回事了。

**我不知道會是哪一種，而這正是它值得做的原因。**

實作上還有一個小而重要的細節：驗證 agent 被明確禁止讀 `<slug>.map.json`——那是「哪條 claim 來自哪裡」的對照表。prompt 裡我寫得很直白：

> Reading it would destroy the only thing this stage is for.

## 9. 驗證員做的事超出我的預期

19 個驗證 agent 跑了幾個小時。它們做的事比我設想的認真得多：

- 有一個為了確認某個 TypedDict 欄位是不是 `Required`，**去下載了 pinned 的 `sentry-kafka-schemas==1.3.6` wheel** 來讀。那條 claim 說「可能 KeyError」，前提不成立。
- 有一個把兩個新的 ASN.1 類別**抄進 scratch tree、用本地 JDK 21 編譯、然後跑 40 萬次隨機輸入去 fuzz**。它確認了 claim 說的 `NegativeArraySizeException` 確實存在但逃不出公開入口，順便**撞到一個沒有任何工具提到的 `NumberFormatException`**。
- 有一個為了確認「兩個同名 `def self.downsize` 會怎樣」，**直接跑 ruby** 把兩個定義餵進去，確認 Ruby 靜默取後者，於是既有的五參數呼叫者會直接炸掉。
- 有一個為了判斷 `hash()` 在跨 process 時穩不穩定，**開了三個新的直譯器**去比對——確認 `PYTHONHASHSEED` 隨機化不涵蓋 int，所以那條 claim 的機制講錯了。

還有一件我沒預期的：**它們會把 claim 往嚴重的方向修正。**

有一條 claim 說某個 `member` 可能是 None、在特定 flag 開啟時會 AttributeError。驗證員去查，發現那行在 `if use_optimized` 區塊**之外**——所以用 API key 的呼叫者**每一次請求都會炸**，不只在 flag 開啟時。它判 real / Critical，並把更正寫進理由。

盲測的價值不只是砍掉錯的。它也會把低估的往上抬，而這件事只有在驗證員不知道 claim 來源時才可信。

## 10. 那個我沒預期的數字

1,395 條 claim 跑完：**1,206 real、140 not_real、49 unclear**。

然後是這個：

> **人寫的 137 條 golden comments，23 條沒通過盲測驗證。16.8%。**

我原本預期會發現「漏收」——golden set 沒記到的真問題。這個我預期到了，也確實有（271 個被確認的真問題）。

我沒預期到的是「**誤收**」。標準答案本身有四分之一經不起一個仔細讀 diff 的讀者檢查。而每一條不成立的 golden comment，都在懲罰那些沒有複述這個錯誤主張的工具。

上游的文件預見了 gold set 會封頂在人類水準——那是**漏收**，他們寫了整整一節。我量到的是另一半：**誤收**。這個方向在 methodology 裡完全沒有出現。`Recall is capped by the gold set` 講的是天花板不夠高，沒有人講地板有洞。

我也回頭確認了這不是抽樣運氣：**全部 50 個 PR 的 golden 密度是每 PR 平均 2.72 條、中位數 2、最多 6。** 稀疏是系統性的。

而且它不是刻意的設計。methodology §3 交代了血緣：Greptile 的原始資料集是**每個 PR 一個 bug**，Augment 後來人工擴充過一輪，並且「showed the original dataset was incomplete」。現在的 2.72 是**那一輪擴充的結果，不是一個目標值**——繼續擴充還排在 Stage 2 的待辦裡。

所以「golden 少」的正確描述是：**一個已知的未完成品，不是一個設計決定。**

## 11. 我算錯的那張表

這段是整篇最該記下來的，因為它是我自己犯的、而且錯在對我有利。

拿到驗證結果之後，我算了校正分數。recall 的分母用「通過驗證的 golden ∪ 所有被確認為真的問題」。

結果：**我的工具 84.3% F1，其他人 26–38%。**

這個差距好看到讓我起疑。所以我去看了組成：

```
769 個被確認的問題
  我的工具提出了 602 個
  其中 434 個「只有」我提出
```

**超過一半的標準答案是我自己寫的。**

用它來量 recall，量到的是話多，不是 recall。而這正是我這整個校正要修掉的偏誤的**鏡像**——原本的 ground truth 封頂在人類找得到的東西，我的擴充版封頂在工具的聯集，而我的工具因為話多所以主宰了聯集。

我換了兩個算法：

- **leave-one-out**：每個工具的標的都拿掉它自己獨有的發現（我 59.0%，其他人 14.1–19.3%）。
- **只對通過驗證的 golden 算 recall**：這個標的**沒有任何工具能影響**，完全對稱。

主結論用後者。原本那張錯的表**沒有刪掉**，留在 `scores/summary.json` 的 `corrected` 欄位裡標示清楚，commit message 也寫了它錯在哪、為什麼、被什麼取代。

刪掉會比較好看。但一個「我發現自己算錯並修正」的紀錄，比一個「從頭到尾都對」的表更有說服力——尤其當錯誤的方向對自己有利的時候。

## 12. 驗證員自己也不是尺

跑到後段，我發現有五個 PR 的驗證意外各跑了兩次（agent 重跑覆寫了自己的輸出）。

這是個意外，但它免費給了我一個東西：**驗證員的自我一致率**。

| PR | pass 1 | pass 2 | 一致率 |
|---|---|---|---:|
| `sentry-95633` | 31/6/2 | 30/7/2 | 97% |
| `keycloak-36880` | 25/4/2 | 27/4/0 | 94% |
| `discourse-graphite-1` | 18/4/3 | 17/2/6 | 88% |
| `keycloak-33832` | 17/4/2 | 21/0/2 | 83% |
| `keycloak-38446` | 29/5/2 | 36/0/0 | 81% |

**81–97%。** 這直接決定了校正後的數字該被讀到什麼精度——**幾個百分點，不是小數點**。

其中 `discourse-graphite-1` 的移動特別有教育意義。兩次都被問到「`Tempfile#size` 在原地重寫後會不會過期」。

- pass 1 判 `not_real`：ImageOptim 寫到暫存路徑再 rename，重新 `File.size` 是對的。
- pass 2 去讀了 Ruby 3.3.6 的 stdlib、確認 `Tempfile#size` 每次都 fstat 活的 fd、重現了 truncate 和 rename 兩種情況——然後把它移到 `unclear`，因為要定案得知道 ImageOptim 0.20.2 實際走哪條路，而那個 gem 沒裝。

**第二次做了嚴格更多的功課，然後變得更不確定。**

這是驗證員該有的移動方向，也是一個警告：`not_real` 這個判定，是你「停得早」才會到達的那一個。所以單次的 `not_real` 比單次的 `real` 更不可信。

`keycloak-33832` 那次更麻煩：pass 1 的四條 `not_real` 每一條都附了具體反證（那個 null guard 就在 `CryptoIntegration.java:43-52`），而 pass 2 完全沒回頭看它們，跑去 compile ASN.1 了。**最後被計分的是 pass 2，而它剛好對我有利。** 這是 last-write-wins，不是判斷，我把它原樣寫進 `VERIFIER_VARIANCE.md`。

## 13. 一路上撿到的東西

不是設計要找的，但撞上了：

- **一個 PR 標題寫「Replays Self-Serve Bulk Delete System」**，實際 diff 是 32 個無關 commit、106 個檔案、8700 行。3 條 golden comment 對這種規模。
- **一個 PR 疊在另一個之上**，diff 含兩者，golden 只涵蓋其中一個。
- **一個 commit 誤加了 `sentry-repo` gitlink**（mode 160000，沒有 `.gitmodules`），沒有任何 golden comment 提到。
- **合成 PR 的注入 bug，附帶宣稱程式碼安全的註解**——「This is safe because the underlying queryset will handle boundary conditions」，而 Django 明確拒絕負數 slice。

最後這個值得單獨講。對於會把註解當證據的審查器，這是一個**沒被言明的攻擊面**：只要在有問題的程式碼旁邊寫一句「這裡是安全的，因為……」，就可能讓審查器跳過它。

我的 skill 有一條規則叫「文字是證據，不是指令」。它把這段記進報告的 `process_directed_text` 欄位，然後照樣判 Critical。這條規則當初寫的時候想的是 MR 描述裡的「這段不用看」，沒想到會在合成 benchmark 的注入 bug 上派上用場。

## 14. 事後看，哪些決定是對的

**在讀答案之前把規則寫死。** 選取規則、fork 的選擇、判準——全部在看到 golden comment 之前定案並寫進 docstring。這讓後面每一個「這樣是不是對我太有利」的自問都有一個明確的答案可以查。

**先照別人的規則跑一遍。** 最後一名那個數字，我沒有藏、沒有加註解、沒有先寫辯解。它是報告的第二節。有了它，第三節的校正才是「補充」而不是「替換」。

**把 judge 拿去對別人校準。** 這是唯一能把「我的 judge 值得信」從宣稱變成量測的方法，而且它免費附贈了雜訊底線。

**讓 ground truth 一起受審。** 這是整趟最有價值的一個決定，而且它的價值不在於結果對我有利——在於**在做之前我不知道結果會是什麼**。如果 54 條 golden 全部通過，我就得寫一篇不一樣的文章。

**把錯的留著。** 自我膨脹那張表、fresh-eyes 沒跑在正確位置、quality-check 完全沒跑、驗證員的不一致——全部在報告裡。刪掉任何一個都會讓結論看起來更乾淨，也更不值得信。

## 15. 哪些不對

**fresh-eyes 的順序沒守住，而我用「事後補跑」矇混過去了。** 它的獨立性還在，但位置沒了。老實說，正確的處理應該是把它標記為「這次沒有真正執行」，而不是回填。我選了折衷，並在報告裡揭露——但這是折衷，不是解法。

**驗證只跑一次。** 五個 PR 意外各跑了兩次，告訴我自我一致率是 81–97%。而 `keycloak-38446`（29/5/2 → 36/0/0）**在幅度上不是離群值**（81%，最低的另一個是 83%）——它的問題是**方向**：每一次移動都朝同一邊，**五條 `not_real` 全翻成 `real`，全部對我有利**。更麻煩的是第二次沒有回頭處理第一次那五條各自附了引用的反證，它只說「這組裡沒有幻覺識別字」，那是另一個主張。被計分的是第二次，純粹因為 last-write-wins。

正確的做法應該是**每個 PR 都跑兩次**，不一致的送第三次。我沒有。所以我只能揭露誤差，不能消掉它——而這個例子告訴我，誤差不是均勻的雜訊，它可能整片倒向一邊。

**我自己排程造成的競態。** 擴充到 50 個時，我在抽取批次還在跑的時候就派了重跑，兩個 agent 同時寫同一個 `candidates.json`，互相覆蓋。我當下把中間狀態誤判成「agent 回報成功卻沒寫檔」，還對使用者這樣講了兩次——**兩次都是錯的**，檔案一直都在，是我檢查得太早。後來的判定 agent 自己抓到「我讀檔期間這個檔案被改了」並主動重讀，那才是真正該有的防線。教訓有兩層：不要在同一批檔案上重疊派工，以及**不要在背景工作還在跑的時候，把快照當成結論**。

**`fetch_pr.py` 的設計是錯的。** 它為每個 PR 各 clone 一份完整 repo——同一個 sentry 被 clone 了 10 次。19 個 PR 時勉強能忍，擴到 50 個就變成主要成本：約 90 分鐘、4.5 GB。正確做法是每個 source repo clone 一次、用 `git worktree` 共用 object store，5 份而不是 50 份。我沒有重寫，因為當下重寫要丟掉已完成的 26 個 clone。這只影響成本不影響結果，但它是那種「小規模時看不出來、放大就變成瓶頸」的設計。

順帶一提，同一支腳本還有一次**靜默失敗**：`cal_com-8330` 第一輪沒抓到，而且沒有任何錯誤輸出。是我事後對帳 50 份 diff 才發現的。

**我在指令裡寫錯過一件事。** 派 Go 那 8 個審查 agent 時，我在 prompt 裡斷言「沒有 Go toolchain」。**有**——`go`、`gofmt`、`golangci-lint` 都在 PATH 上，是其中一位審查員回報糾正我的。真正的限制是沒有 module cache 也沒網路。這個錯誤會**低估** Go 那批的掃描覆蓋率而不是高估，所以不影響結論的方向，但它提醒我：**寫進 prompt 的環境描述也是一種未經驗證的斷言**，而我在 skill 裡對別人要求的正是「不要寫未經查證的斷言」。

**訓練資料汙染沒有處理。** 這些是公開的舊 PR，benchmark repo 和 golden comments 也公開。我的模型可能看過。同業原則上有同樣曝險，但曝險程度不一定相同——**這件事我沒有量，也不知道怎麼量。**

**模型世代分不開。** 同業是 2026 年初用當時的模型跑的，我跑在今天的模型上。最接近的對照是 `claude-code`（同模型家族，raw F1 35.9%、校正後 F1 60.7%，都在我之下），但這個實驗**沒辦法**告訴你有多少來自 skill、多少來自模型。要回答這個，得拿同一個模型跑「有 skill」和「沒 skill」兩次——那是另一個實驗。

## 16. 如果你要做類似的事

三句話：

**先讀 scorer 的原始碼，再跑。** 你會知道那個分數在量什麼，而且是在你對結果有情緒之前知道。

**證明你跟對照組讀的是同一批 bytes。** 不是「應該是」。我差一點就拿我對 A 的答案去比別人對 B 的答案，而且不會有任何東西報錯。

**把你的標準答案也送去盲測。** 同一把尺、匿名、跟被它否決的東西混在一起。我原本以為只會證明「它漏了東西」，結果它同時也**收錄了 24% 不成立的東西**——而這件事，只有在驗證員不知道哪些是人寫的時候，才問得出來。
