# ADR 0003：重連後不做 server-side 畫面重播，依賴 TUI 自身重繪

- 狀態：已接受

## 背景

dockerd 不保存終端「目前畫面狀態」。客戶端斷線後重連 attach，只會從重連那一刻開始
收到新 bytes——在下一次輸出發生前，畫面是空白的。

可選的補救曾包括：`docker logs` 重播、server-side 終端模擬（pyte 之類）維護螢幕狀態、
或不補救依賴 TUI 自身重繪。

## 決策

**不做任何 server-side 重播或螢幕狀態維護。**

- **不走 `docker logs` 路線**：長時間 session 的 raw 歷史動輒巨量，從頭重播成本高；
  `--tail` 又會從 escape sequence 中間切開、弄花畫面。
- **不引入 pyte**：在「主要互動對象是一個會自己重繪的 TUI」的前提下，重繪由應用自己
  解決，不值得為此維護一套 server-side 終端模擬。

重連後的畫面恢復依賴：

- **自刷新型 TUI**（top、含 spinner 的執行中畫面）：下一輪刷新自然恢復（spike 實測 top
  於 2.1s 內完整重繪）。
- **等輸入型 TUI**：任一按鍵即觸發全畫面重繪（spike 以 curses idle TUI 實測證實；
  Ink 框架同屬輸入驅動重繪）。使用者重連後的第一個動作就順手解決了。

## 後果

- 核心層零額外複雜度；重連語意簡單誠實：「從現在開始看」。
- 犧牲：斷線期間的輸出不可回看（scrollback 不跨連線），重連瞬間畫面短暫空白。兩者
  均已知悉並接受。
- 若未來出現「重連即需完整畫面」的硬需求（如唯讀觀看端），屆時再評估 pyte 維護螢幕
  快照——`docker logs` 重播不再重新考慮。
