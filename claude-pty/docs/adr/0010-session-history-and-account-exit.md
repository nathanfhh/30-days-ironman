# ADR 0010：session 歷史永久留存、帳號退場＝管理員改密碼（不刪除、不停用）

- 狀態：已採用
- 相關：[0004](0004-flask-control-plane.md)、[0008](0008-persistent-registry-and-on-demand-ttyd.md)

## 脈絡

[ADR 0008](0008-persistent-registry-and-on-demand-ttyd.md) 把 registry 放進 DB，但
`sessions` 表一直被當成「當下狀態」：session 結束時登錄列直接被 DELETE。於是「誰在什麼
時候、用什麼 profile、開了什麼 session」隨著容器一起消失。

同一個問題的另一面在帳號：刪除使用者會沿 FK cascade 掉他還沒歸檔的 `sessions` 登錄，
但容器不會被刪——變成沒人認領的孤兒；而且刪除不可逆，連帶把操作歸屬一起抹掉。

## 決策

### 1. 結束的 session 搬進 `session_history`，永久保留

`sessions` 繼續只放「進行中」的（要被對帳、算配額、跟 dockerd 比對）。結束時把快照搬進
`session_history` 再刪列，**同一個交易內完成**，不會出現「刪了但沒留下紀錄」的中間狀態。
`archive(sids, reason)` 是 session 結束的**唯一出口**；任何直接 `s.delete(SessionRow)`
都會讓那段歷史憑空消失。

`ended_reason` 記錄怎麼結束的：`terminated` / `exited` / `gone` / `idle`。**歷史存的是
快照不是外鍵關聯**：`username`、`profile`、`workdir` 都存當下的值，`user_id` 是
`ON DELETE SET NULL`——帳號日後被改名，歷史仍讀得出當時是誰開的。不設保留期（稽核用途，
一列不到 1 KB）。

### 2. 帳號的退場＝管理員改掉他的密碼；**沒有刪除，也沒有「停用」狀態**

- **不刪除**：沒有 `DELETE /api/users/<uid>`，`auth` 模組也沒有 `delete_user()`。理由與
  第 1 點直接衝突：留存歷史是為了稽核，而刪除會 cascade 掉還沒歸檔的進行中 session，
  那段歷史沒經過 `archive()` 就消失、容器卻還在跑。
- **沒有 `is_active` 這個狀態**。退場的做法是**管理員改掉他的密碼**，它做到的是這三件：
  1. `password_version` 遞增 → 他既有的 cookie 全部當場失效；
  2. 呼叫端**嘗試**切斷他目前追蹤得到的互動終端（cookie 的版號管不到一條已升級完成的
     WebSocket：授權只發生在連線交出去之前，之後不會再有人回頭問它還算不算數，所以要
     主動切）。這一步**可能失敗，失敗會回報**；
  3. 他不知道新密碼，登不回來。
  ⚠ **這三件不等於「停用」，也不等於撤銷。** 他的 session 容器繼續跑、背景工作繼續跑、
  他存的 GitLab PAT 與 per-user proxy 都還在。這個決定換到的是**少維護一個狀態**（不必有
  is_active 欄位、不必在登入與 gate 各查一次、也不必替「停用最後一位管理員」造一道專屬
  防線），代價就是上面那三樣東西不會因此停止。缺口逐條列在下面。要讓他回來，就把新密碼
  告訴他。

  ⚠ **2026-08-23 修正：這裡原本寫「三件合起來與『停用』的效果相同」，那句話不成立，
  已刪除。** 這個決定本身（不刪除、不做停用狀態）維持不變，被推翻的只有那個等價宣稱。
  缺口是具體的四條：

    · **他的容器繼續跑。** 這是設計（切存取權不終止工作，見 ADR 0003 與本文），
      但它意味著他名下的 session 還活著，不是「什麼都停了」。
    · **他存的 GitLab 憑證與 per-user proxy 還在**（ADR 0016）。改密碼刻意不動它，
      因為改密碼是例行操作；代價是那條對外的路不會因為改密碼而關上。
    · **收終端可能失敗。** 以前失敗會被 `suppress(Exception)` 吞掉、畫面照樣回成功；
      現在 `close_user_views` 回 `(收掉幾個, 失敗幾場)`，API 與 CLI 在有失敗時不回 204。
      但「回報得出來」不等於「一定收得掉」。
    · **收終端是一次快照，不是一道閘**（2026-08-23 複驗補上）。`close_user_views` 先列出
      要收的 session、再逐一收；在那之間，一個已經通過 `before_request`、還沒跑到
      `open_view` 的併發請求仍然開得出新的 ttyd，而它不在那份快照裡。窗口是一個請求
      週期，很窄，但存在。**修法不在收終端那一側**：要關掉它，`open_view` 得在真正建立
      之前再問一次帳號狀態，也就是下面那個「這個工具沒有做」的東西。沒有那個狀態，
      在這裡再補都只是把窗口變窄。

  同一輪也補上 `View.actor_user_id`：以前 view 只掛在 session 上、不記得是誰在看，
  所以「改掉一位 admin 的密碼」收不掉他正開在**別人** session 上的終端。

  要真正的撤銷語意（不能再登入、憑證作廢、工作終止、失敗可重試），需要一個獨立的帳號
  狀態加一條對帳迴圈。**這個工具沒有做，也不假裝有**——半套的撤銷比誠實的沒有更危險，
  使用者會以為帳號真的關掉了。

  這也意味著**管理員可以拿走任何人的帳號**。那是這個權力的一體兩面，寫在 README 的安全
  邊界一節：開帳號給誰，就等於請他信任你。
- 沒有事後的提權 / 降權端點：**權限只在建立帳號時決定**。設錯了就再建一個對的，然後把
  設錯那個的密碼改掉讓它退場。

改密碼（不論自己改或管理員代改）一律**沒有「操作中的這一台除外」的特例**：這個帳號現在
的**登入狀態與互動終端**全部斷掉，包含按下送出的那一台。留一個例外只換到少按幾個鍵，
卻讓「全部失效」變成說一套做一套。
（範圍就是登入狀態與終端這兩樣。容器與背景工作不在內，見上面那段。）

登入失敗訊息與帳密錯誤**完全相同**，不回饋「這個帳號存在」。

## 後果

- 「何時開過哪些」永久查得到，且不受帳號生命週期影響（`GET /api/sessions/history`）。
- `sessions` 表維持小而純，配額計算與對帳邏輯不必再過濾已結束的列。
- 代價：使用者名稱不可回收（`username` UNIQUE）——撞名是小麻煩，稽核鏈斷掉不是。
- schema 演進：新表由 `create_all` 建立。⚠ 輕量升級**只補欄位本身**，既有表上新增的
  index 與 UNIQUE 一律不會被追溯套用，所以 `session_history.session_id` 的 UNIQUE 必須在
  建表當下就存在。
